# Багфикс

Отчёт об ошибке — тоже спецификация: каждое заявленное в нём поведение должно держаться после правки так, как держалось до. Где формулировка двусмысленна, повторяй то, что неисправленный код на этом пути уже делал — меняется только заявленный дефект.

- Чини причину, а не место, где виден симптом. Когда формулировка задачи задаёт ожидаемое поведение («вместо»), это замена, а не добавление.
- Прежде чем править, найди через grep всех вызывающих трогаемой функции и исправь один раз в общем коде.
- Если падающая проверка фиксирует старое поведение, которое задача просит изменить, не угадывай замену по словам задачи: реализуй через канонический механизм, который уже даёт окружение (установленная библиотека, стандарт платформы), а не пиши вручную свой путь или формат. Когда для этого нужна сторонняя библиотека, от которой проект пока не зависит, добавь её в манифест зависимостей (setup.cfg / pyproject.toml / package.json) — чистая установка должна продолжать работать.
- Когда проект — публичный репозиторий, ищи каноническое исправление в его истории (`git log -S` в рабочей копии, выпущенная версия из реестра), а не восстанавливай по памяти. Переноси весь набор изменений, а не только hunk ближайший к симптому: когда исправление переносит работу между местами, обнови каждое место, которое потребляло старое поведение. Когда каноническое изменение шире, чем подсказывает симптом (глобальный флаг, более свободная грамматика), сохрани эту широту и подстрой соседний код, вместо того чтобы сузить правку ради вида безопасности.
- Выводи проверку из контракта, а не из патча: каждое заявленное в отчёте условие становится утверждением, включая тот крайний случай, который отделяет исправленное от неисправленного (чтение после истечения срока, запись по устаревшему индексу). Проверяй через ту дверь, которой пользовался отчёт — функция, на которой отчёт показывает ошибку, сама стоит внутри утверждений и спрашивается по обе стороны границы исправлено/не исправлено.
- Дай этой проверке её негативный контроль в том же единственном прогоне: сначала она идёт против неисправленного кода и падает там, затем проходит после правки. Один зелёный прогон это решает — негативный контроль не второй прогон, и базовый замер через `git stash` для него не нужен. Наблюдатель, который соглашался ещё до правки (`has`, `size`, строка лога), дефект не видит и ничего не доказывает.
- Если твой скрипт и код расходятся, что из них врёт, решает контракт — никогда не ослабляй проверку, чтобы стало зелено.
- Временный тест или фикстура, написанные только чтобы проверить эту правку, удаляются до того, как ты закончил, если задача не просила тестов: чистый diff несёт только исправление, а черновые файлы, оставленные в тестовом дереве проекта, ломают любой патч, положенный сверху.
