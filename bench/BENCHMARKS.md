# Официальные бенчмарки кодинг-агентов: обзор и что брать в Acpio

Исследование от 2026-09-30, вердикты пересмотрены в тот же день после проверки
свежести лидербордов (см. §3: polyglot демотирован). Вопрос: какие
**официальные** бенчмарки существуют, что они меряют, сколько инфраструктуры
требуют и что из них портируемо в наш бенч (`bench/`), чтобы сравнение
builtin vs pi/omp опиралось не только на самодельные задачи.

## 1. Контракт нашего бенча (что ограничивает портируемость)

- Среда: воркспейс-каталог, агент действует инструментами
  `read/write/edit/bash/grep/glob`; Windows-хост, Git Bash, Node 24.
- Проверка: скрытый `verify.mjs`, ноль сети, детерминизм, 15–120 с на задачу.
- Anything Docker/Python/pytest = отдельный режим, не быстрый цикл итераций.

## 2. Обзор ландшафта

| бенчмарк | что меряет | инфраструктура | языки | масштаб |
|---|---|---|---|---|
| [SWE-bench Verified](https://www.swebench.com/) | правка реальных Python-репо по issue, скрытые fail-to-pass тесты | Docker на задачу, pytest | Python (12 репо) | 500 задач, валидировано OpenAI |
| [SWE-bench Pro](https://scale.com/leaderboard/swe_bench_pro) | то же, устойчивое к запоминанию | Docker | Python+другие | 1865 задач: 731 публичных + ~1100 приватных |
| [Multi-SWE-bench](https://github.com/multi-swe-bench) | реальные issue/PR в популярных репо | Docker, тесты репо | JS/TS, Java, Go, Rust, C/C++ | ~500+ инстансов (JS: axios, express, pouchdb…) |
| [Terminal-Bench 2.0](https://www.tbench.ai/) | агент в реальном терминале: компиляция, серверы, пайплайны | Docker-песочница + verifier-контейнер (`tests/Dockerfile`), harness [harbor](https://github.com/harbor-framework/terminal-bench-1) | любой (внутри образов) | 89 задач 2.0; экосистема 3500+ окружений |

| [LiveCodeBench / HumanEval+](https://livecodebench.github.io/) | алгоритмические задачи со скрытыми тестами | минимальная | Python/на выбор | сотни задач |
| [DeepSWE / R2E-Gym](https://agentica-project.com/) | RL-среды: коммиты → задачи с генерированными тестами | Docker + Python | Python | 113 (DeepSWE) / 8k+ (R2E-Gym) |

Полезные оговорки из литературы: у SWE-bench Verified аудит нашёл ~28.5% задач
со слабыми тестами (неверный патч может пройти) и выраженное **запоминание**
моделями популярных задач — именно поэтому появился SWE-bench Pro с приватным
холдаутом. **Aider polyglot как лидерборд фактически заморожен**: обновления
редкие и волонтёрские — GPT-5 добавили одиночным прогоном, Opus 4.1+,
GPT-5.1/5.2 и новейшие Claude не прогонялись вовсе (открытые issue с
требованиями обновить), сообщество для свежих сравнений использует
LiveCodeBench, SWE-bench и агрегаторы.

## 3. Вердикты по портируемости (пересмотрены 2026-09-30)

### Ярус 1 — брать первым: **SWE-bench Verified (подмножество)**

Единственный корпус со всеми тремя нужными свойствами сразу: индустриальный
стандарт с живыми, регулярно обновляемыми числами; скрытые тесты
(FAIL_TO_PASS / PASS_TO_PASS); готовые официальные Docker-образы на каждый
инстанс — вся среда уже собрана. Механика полного переиспользования их
верификации нашими harness'ами — §4.1. Брать 3–10 инстансов из **быстрых**
репозиториев (astroid и т.п.), не случайную выборку: тяжёлые сюиты (django —
десятки минут на прогон) убьют быстрый контур.

### Ярус 2 — **Terminal-Bench**, маршрут А (портирование каталогных задач)

Активный проект (Laude Institute, TB 2.0 — 89 задач, свежие лидерборды
агентных harness'ов), ближайший к нашей модели «агент в шелле». Маршрут А:
задачи, чья среда — «файлы в каталоге», портятся в наш формат 1:1, их
`tests/` становится нашим скрытым верификатором (запуск на хосте — Python
3.14 установлен). Полный Docker-режим нашего runner'а (маршрут B) — дальний
этап, см. план §5.

### Демотирован (2026-09-30): **Aider polyglot, JS-подмножество**

Был кандидатом в Ярус 1 как единственный корпус, импортирующийся без
инфраструктуры (упражнения Exercism самодостаточны, для JS нужен только Node).
Снят с приоритета по трём причинам:

- **лидерборд заброшен** — свежие frontier-модели не прогоняются, «лучший
  опубликованный результат» принадлежит модели годичной давности (GPT-4.1,
  ~88%); для «официального» числа это дисквалификация;
- насыщение: вершина упёрлась в практический потолок, дискриминативность
  между сильными моделями потеряна;
- слабый агентный сигнал: типичная задача — 1–2 вызова инструментов
  (написать файл, прогнать тесты) — не трогает ни навигацию по репо, ни
  многофайловые правки, ни восстановление после ошибок; ровно это уже меряет
  наша swe-семья с генератором-валидатором.

Контаминация (задачи публичны с конца 2024) для сравнения harness'ов на одной
модели была бы не важна — все три агента стартуют с одинаково известных задач.
Возвращать в план только по явной нужде в дешёвой семье pass-rate. Лицензии,
если вернёмся: aider — MIT, Exercism problem-specifications — CC BY-SA 4.0.

### Ярус 3 — по мере надобности

- **SWE-Lancer IC SWE**: настоящий JS/TS-репо (Expensify) со скрытыми
  e2e-тестами — самый близкий к «реальной работе» бенчмарк, но требует всего
  репо; тяжёлый, хорош как периодическая глубокая проверка.
- **Multi-SWE-bench JS/TS**: реальные issue/PR в axios/express/pouchdb;
  Docker + тесты репо; средняя тяжесть между Verified и Lancer.
- **SWE-bench Pro**: приватный холдаут = защита от контаминации, но доступ
  гейтится вендором; смотреть как на внешнюю валидацию, не как на локальный
  инструмент.
- **LiveCodeBench/HumanEval+**: алгоритмокатки — не добавляют ничего к нашим
  задачам, пропускаем.
- **DeepSWE/R2E-Gym**: методика уже перенесена (swe-семья); контейнеры — нет.

## 4. Рекомендация — и главный принцип, который всё расставляет

**Цель сравнения одна: наш harness против pi и omp. Значит, runner — всегда
наш бенч, и никакого другого harness для сравнений не существует.** Запустить
задачи через harbor или swebench-harness означало бы измерить их агентный
цикл, их промптинг и их инструменты — переменная, которую мы сравниваем,
исчезла бы. Официальные бенчмарки ценны для нас **только как корпус задач и
скрытых проверок** (то, что делает задачу «официальной»), а не как способ
гонять агентов.

Отсюда двухуровневая система:

1. **Быстрый контур (наш бенч, минуты)** — плагинные + swe-задачи: итерации
   улучшения агента, каждый день. Метрики: uncached, шаги, toolErr, pass-rate
   по семьям раздельно. Runner — `bench/run.mjs` через прокси, как всегда.
2. **Официальный корпус задач в нашем runner'е** — SWE-bench Verified
   подмножество первым (их образы + их тесты, наш прогон); Terminal-Bench
   маршрут А следом. Если когда-нибудь захотим задачи, которым нужен
   настоящий Docker как среда — это будет расширение нашего runner'а
   (контейнер как воркспейс для всех трёх агентов одинаково), а не переход на
   их harness: equal footing для всех трёх агентов важнее «официального
   протокола».

**Решение 2026-10-01: дефолт всех прогонов бенчей — докер.** Повседневные
прогоны `bench/tasks` идут через `bench/run-docker.mjs` — та же песочница, что
у SWE-контура: образ `acpio-daily-sandbox`, контейнер на слот, чистый
`/workspace` на пару, скрытый верификатор исполняется внутри контейнера; все
три агента в равных условиях внутри. Хостовый `bench/run.mjs` остаётся быстрым
dev-контуром — итерации по самому раннеру и экспресс-проверки, — но записи в
сравнениях агентов делаются в докере. Этим снимается прежний статус
«docker-режим — дальний этап»: `run-docker.mjs` реализован и становится
основным способом запуска.

Важно про Docker-задачи и builtin: инструменты builtin работают через хост
(fs/terminal), pi/omp — через собственный процесс. Ставить контейнер между
агентами и средой можно только одинаково для всех трёх (например, все три
внутри контейнера с Node), иначе само сравнение harness'ов искажается.
Поэтому Docker-как-среда — не следующий шаг, а самый дальний.

## 4.1. Как именно используем их верификацию

Схема «выполняем задачи нашими harness'ами, верифицируем их артефактами» —
да, это работает, и по обоим корпусам механика конкретная:

**SWE-bench Verified — самый удобный.** У каждого инстанса есть официальный
Docker-образ (`swebench/sweb.eval.x86_64.<repo>:<id>`): репозиторий уже на
нужном коммите, среда собрана, тесты на месте. Наш runner:
1. агент (pi/omp/builtin — наш прокси, наши метрики с провода) правит хостовый
   чекаут репо на базовом коммите;
2. runner снимает diff воркспейса;
3. diff применяется внутри их образа, запускается их pytest;
4. вердикт — по их же спискам: все FAIL_TO_PASS зелёные и ни один
   PASS_TO_PASS не сломан.
Ни одной части их harness не задействовано — только образ, тесты и списки.

**Terminal-Bench — два маршрута.** Их `tests/` — просто скрипты верификации,
их можно звать напрямую:
- Маршрут А (селективный, быстрый): задачи, чья среда — «файлы в каталоге»,
  портятся в наш формат 1:1, их `tests/` становится нашим `verify` (на хосте —
  Python 3.14 на машине есть).
- Маршрут B (полный Docker-режим нашего runner'а): производный образ (их образ
  + слой с Node), все три агента запускаются внутри контейнера, верификатор —
  там же. Идентичная среда для всех трёх — обязательное условие (см. выше про
  builtin и хост).

**Подводные камни, знать заранее:** у Verified тяжёлые сюиты (django — десятки
минут на прогон тестов) и образы по 1–3 ГБ на инстанс — брать подмножество из
быстрых репозиториев; в образах Terminal-Bench нет Node — маршрут B требует
производного слоя; Windows Docker Desktop добавляет нюансы с путями.
Агентная часть pi/omp в маршруте B должна исполняться в том же контейнере,
иначе сравнение harness'ов искажается.

**Что не берём никогда:** их агентные скэффолды (harbor, swebench-harness,
адаптеры агентов) — только task-артефакты: инструкция, среда, тесты, списки.
